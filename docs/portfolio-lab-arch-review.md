## 一、ETF 的口径：~~🔴 架构错误~~ → ✅ **已裁决：不是 bug，是"产品选择"**（2026-09-19 用户裁决）

> **用户裁决原文**：「蛋卷是场外基金，纳指场外和场内本身就有溢价，不同的纳指基金场外基金本身收益也不一样，**这个可以接受。允许用户选择不一样的同类产品。**」
>
> **含义**：① 场内/场外的溢价、不同场外基金的收益差异，都是**产品本身的差异**，不是需要修正的口径错误；② 系统**两种口径都要支持**——`HFQ_PRICE`（腾讯市场价）与 `NAV_ADJ`（蛋卷净值）并存；③ **用户自主选择具体产品**：想跟踪场内成交价就加 `513100`（场内 ETF），想对齐韭圈儿净值口径就加对应的**场外纳指基金**（蛋卷）。
>
> **对实现的影响**：`data-maintenance.md` 的原始拆分**成立**（个股/ETF → 腾讯，场外基金 → 蛋卷）；`verify_against_funddb.py` 的回归**依然有效**——它验证的是**净值口径复刻韭圈儿**这条路径（用户选场外产品时）；用户若选场内产品，则得到市场价收益（与韭圈儿不同，**合理且如实**）。
>
> 下文保留为问题发现过程的记录（实测数据仍有效，结论已由"修正"改为"接纳"）。

**问题**：验收与生产**不是同一条数据口径**。

| | 验收（`verify_against_funddb.py`） | 生产设计（`data-maintenance.md`） |
| --- | --- | --- |
| 场外基金 | 蛋卷净值 | 蛋卷净值 ✅ 一致 |
| **ETF（513100）** | **蛋卷净值** | **腾讯场内价** ❌ **不一致** |

**实测差异（近10年，2016-09-14 ~ 2026-09-17）**：

| 标的 | 蛋卷净值口径 | 腾讯场内价（hfq） | 差 |
| --- | ---: | ---: | ---: |
| **513100 纳指ETF** | **490.22%** | **578.53%** | **+88.30pp** 🔴 |
| 161116 黄金LOF | 111.06% | 112.81% | +1.75pp |

> 腾讯 hfq 已正确处理份额折算（2022-01-13 前后净值序列平滑、无 −77.78% 跳空），所以这 88pp 是**真实的溢价扩张**（纳指ETF 常年溢价且近年走高）+ 复权方式差异，不是数据错误。
>
> **结论：韭圈儿用的是净值口径**（我们能复现 490.01% 就靠它）；**如果生产环境把 ETF 归到腾讯场内价，同样的组合会算出 578% 而不是 490%——回归测试会通过（它用蛋卷），但页面数字与韭圈儿完全对不上。**

**为什么以前没发现**：回归测试让**全部 4 个标的都走蛋卷**，把"513100 是 ETF"这个事实掩盖了。验收用的路径与生产设计的路径在 ETF 上分叉，而回归测试只在蛋卷这条路径上跑。

**修正（推荐）**：

| 资产 | 源 | 口径 | 说明 |
| --- | --- | --- | --- |
| **个股** | 腾讯 `fqkline` | `HFQ_PRICE`（市场价格） | 蛋卷没有股票（它是基金平台） |
| **ETF / LOF / 场外基金** | **蛋卷 `djapi`** | `NAV_ADJ`（净值） | **统一净值口径，与韭圈儿一致** |
| **指数（基准）** | 易方达 | `PRICE_INDEX` | 仅基准对照用 |

- **好处一**：回归测试与生产**回到同一条口径**，验收可信。
- **好处二**：ETF 的复权不再依赖腾讯的 `hfq`（对 161116 这类 LOF，腾讯**只返回 `day`、无 `hfqday`**——之前就踩过），统一由蛋卷 `percentage` 链式生成，逻辑更一致。
- **代价 / 边界**：① 若某 ETF 不在蛋卷（小众品种）→ 回退腾讯场内价，但**显式标记 `price_basis=HFQ_PRICE` 并在页面提示口径不同**（此 ETF 不参与与韭圈儿的精确对齐）；② `HFQ_PRICE`（股票）与 `NAV_ADJ`（ETF/基金）同为"分红再投复权"但算法不同 → 混在一个组合里的可比性属 D3，**建议做一次小验证**（已在索引 §四-4.3-5 登记）。

> ⚠ **这意味着 `data-maintenance.md` 需要修订**：`research_daily_sync`（腾讯）应只服务**个股**；ETF 应归入 `fund_nav_sync`（蛋卷）。详见文末"需要同步修改"。

## 二、产品层 review（用户：易交互 / 好用 / 简单）

核心闭环是**真的简单**：`组合列表 → 点卡片 → 切平衡/选区间 → 看结果`。问题全部集中在"加标的"这一步和"行话"上。

### 🟡 建议砍掉的 3 处

#### P1. 「查看态 / 编辑态」两个态 —— 可能是在解决一个不存在的问题

> 出处：`add-asset-ux.md` §六-①（**本来就标着"仍待确认"**）

我们的理由曾是"复刻韭圈儿的清爽 + 增强的灵活，互不干扰"。但冷静看：

- **这是个人工具**，只有一个用户。没有"浏览者 vs 编辑者"的角色区分。
- 韭圈儿要区分态，是因为它要承载"别人的组合 / 官方组合 / 自己组合"——**我们没有这些**。
- 多一个态 = 多一个按钮、多一次切换、多一层心智。

**建议：删掉两态，详情页直接可编辑。** 保留"复刻韭圈儿"的方式不变（视觉照搬），只是把"编辑组合"按钮和"查看态"这个状态去掉。**减一个状态、一个按钮、一次切换，换来的清爽远超"模式分离"那点理论上的好处。**

> 这是产品判断，不是技术对错。如果你坚持要"防误触"，那保留两态也可接受——但请明确那是"防误触"，不是"角色分离"。

#### P2. 「复权口径」是行话，不该让用户看到

`add-asset-ux.md` 的确认卡要求显示 `HFQ / NAV_ADJ / PRICE`。这三串字母对目标用户（看韭圈儿的个人投资者）**没有信息量**，只会让人停下来想"这是什么、我该担心吗"。

**建议**：技术上保留 `price_basis`（后端、回归、排错都要用），但**前端不显示**；只在"口径不同"的异常场景（比如某 ETF 退回了场内价口径）才提示一句人话："**这只 ETF 用的是场内价格，与基金净值可能有差异**"。

#### P3. 「起点被推后」的提示，措辞必须换成收益视角

加一只 2020 年上市的 ETF 到一个 2013 年起的组合，组合的共同起点会被推后到 2020。现在的提示草稿是"新起点 = 2020-01-01（由 513100 制约）前移 9.4 年"——**"制约"和"前移"都是工程师语言**，用户看不懂。

**建议**：换成收益视角的直白说法：

> ⚠ 加入这只 ETF 后，**回测只能从 2020 年开始**（它 2020 年才上市，原组合能从 2013 年开始）。
> [ 仍然加入 ]  [ 不加了 ]

用户要能理解"我的'近10年'没了"意味着什么，而不是理解"共同起始日"这个词。

### 🟢 已经是对的（不要改）

| 设计 | 为什么对 |
| --- | --- |
| 列表页只放三格收益（日收益/近一月/今年以来） | 照韭圈儿，轻 |
| 涨红跌绿 | 符合 A 股习惯 |
| 类型 chip（股票/ETF/基金）+ 冲突列候选 | 解决六位数字三义冲突，真实痛点 |
| 平衡切换 = 三个 tab | 复刻韭圈儿，无学习成本 |
| `近1日` 用合成口径（QDII 前值补偿） | 与韭圈儿一致 |

### 🟠 一个没法回避、只能缓解的摩擦：名称搜索

用户**按名字想标的**（"红利低波 ETF"），我们一期**只能按代码加**。雪球搜索接口需要账号 token 且只覆盖场外基金（股票/ETF 搜不到）。

**缓解（不动架构）**：① 添加框的占位符直接写"**输入代码**，如 512040"；② 把用户**已经添加过的标的**做成本地模糊搜索（自己用得越多个人的可用池越大）；③ token 就位后再开全量名称搜索。**这是现状下性价比最高的路径，不要为此改动后端。**

| 复用 | 评价 |
| --- | --- |

**这部分不需要任何重构，是整套设计里最稳的一块。**

### 🟡 5 处需要现在就想清楚的

#### C1. 双口径并存 = 双份存储、双套心智

个股走腾讯（市场价）、ETF/基金走蛋卷（净值）。同一个资产，如果被**同时**用在 `/research`（做T回放，要市场价）和**组合回测**（要净值）里，就会**存两份**（`research_daily_bar_*` 一份市场价、`fund_nav_daily` 一份净值）。

- **接受它**：两个用途要的本来就是**不同口径**（做T 要你真实成交的市场价；回测要韭圈儿的净值）。**存两份是对的，但必须在文档里写清楚"同一个代码在两个表里的语义不同"**，否则以后一定有人拿错。

#### C2. 文档量太大（9 份 + 约 2,100 行）—— 建议 P3 后蒸馏

为**一个模块**配 9 份专题 + 3 个工具，本身就是维护负担。而且我们已经给多份文档加了"作废记录""更正记录""⚠ 更新块"——**这是设计在收敛过程中留下的脚手架**。

**建议**：P0~P3 落地后，做一次**蒸馏**——把"口径速查 + 算法 + 页面 + 数据维护"合并成 **1 份架构文档**（<400 行），验收报告和回归工具**保留**，其余全部归档到 `docs/archive/`。**现在不动，但要把"蒸馏"写进 P3 的收尾任务里。**

#### C3. 单标的同步有两条可观测路径，建议收敛为一条

定时/批量抓取的日志在 `TaskRunLog`（job 级）；单标的即时同步写到 `research_security` 的 4 个字段（`last_sync_*`）。**两处看数据新不新鲜，以后排障要两边翻。**

**建议**：保留 security 字段（前端轮询体验好，这点不变），但**同时**把单标的同步也写一条 `TaskRunLog`（job_id 带后缀如 `fund_nav_sync:100018`），数据管理页可以加"按标的筛选"。**多写一条日志的成本极低，换来观测路径统一。**

#### C4. `.OF` 后缀引入的潜在崩溃点 —— 未全量排查

`_assert_symbol_type` 依赖交易所后缀，我们给场外基金引入 `100018.OF`。但**没有排查所有会调 `_symbol_exchange()` 的代码路径**——任何一个"假设 symbol 一定有 `.SH/.SZ`"的地方，遇到 `.OF` 都会炸或返回错值。

**建议（P0 开工第一件事）**：`grep -rn "_symbol_exchange\|\.SH\|\.SZ\|split('.')\|rsplit('.')" backend/` 全量过一遍，给 `.OF` 一个统一、显式的处理分支（**宁可报错，不要静默拼成 `sh100018`**）。

#### C5. 回测的"异步"在 V1 是过度设计

`flow.md` 设计为 `POST /backtests` 异步返回 `run_id` 再轮询。但一个 3~10 标的、5000 个交易日的组合，`NAV = Σ nᵢ·Pᵢ` 也就几万次浮点运算 + 几次 DB 查询，**毫秒~秒级**。

**建议 V1 同步**：`POST /backtests` 直接返回结果（`run_id` + 完整指标）。**省掉轮询、省掉前端等待态、省掉一个并发问题。** 等真出现"全市场扫描 / 参数网格搜索"这类慢任务，再上异步。

### 🟠 两个"已量化、接受但要记住"的边界

| 边界 | 量级 | 备注 |
| --- | --- | --- |
| 蛋卷 `percentage` 只有 2 位小数 | 链式 20 年累积约 **0.4%** | 这是「成立来 +1.27pp」残差的来源之一。**不是 bug，是数据精度天花板**——任何复权方式都改不了它，只能如实标注容差 |
| `HFQ_PRICE` 与 `NAV_ADJ` 混合可比性 | 未验证（D3） | 同为"分红再投"但算法不同。**P2 做一次小验证**，确认混合组合里两者不打架 |

## 零、一句话结论

**方案的方向我完全认同，"数据 → 页面"必须升级为"数据 → 因子 → 状态 → 组合 → 回测 → 归因 → 执行"。基于代码核查，有三点是方案没有充分考虑的：**

1. **`/research` 不是空白，它已经是整套"实验范式"的现成样板。** 它有 Run ID（参数即身份的唯一键）、输入哈希、算法版本号、训练/验证切分、逐日明细、九类日分类、对比接口，以及结构性防前视。组合回测应该把这套范式抽象出来复用，而不是另起炉灶。**【代码事实】**
2. **方案想新建的 `asset_master`，八成已经存在于 `index_universe`。** 它已经做了三配置合并、dataset 绑定、`symbol`/`storage_code` 解耦（正是解决"ETF 代码 vs 指数代码"的关键设计）、运行时落点、任务路由。补字段即可。**【代码事实】**
3. **回测基准的收益口径，方案完全没提，但它决定所有结论的方向。** 现有指数日线来自易方达 `index_eod_price`，**只有 close 一个字段**，从接口命名与字段判断是**价格指数**、不含股息再投入。红利资产的收益有相当部分来自股息，用价格指数当 Benchmark 会系统性低估红利收益——偏差量级可能达到每年 4~6 个百分点，**比策略本身的效果还大，且方向偏乐观**（会人为抬高"多资产组合改善回撤"这类结论）。**这必须在写第一行回测代码之前定下来。**

另外有一条**仍需线上确认**的统计约束，见 §1.4：红利估值择时的可用区间受限于该指数估值数据的历史长度，若确为 2017-05 起，则独立样本数 N_eff 仅约 2~4 个，**统计上答不了**"估值择时有没有用"。这一条不依赖本地库，请对照线上确认。

## 一、关于数据：撤回 v1 的推断，改为待确认清单

### 1.1 结论

**v1 中"数据缺口"整节作废。** 线上数据齐全，本地库只是没跑定时抓取。以下推断全部撤回：

| v1 的推断 | 实际情况 |
| --- | --- |
| "指数股息率只有 2 天，不可回测" | ❌ 误判。股息率数据源返回**全历史序列**（见下） |
| "国债收益率只有 2 年" | ❌ 误判。本地 474 行 = 单页截断数，数据源是 **2005 年起全量** |
| "只入库 4 个指数日线" | ⚠️ 本地现象，线上应为配置中的全部标的 |
| "转债无历史截面" | ❌ 误判。`cb_daily_snapshot` 是每日全市场截面，历史按日累积 |
| "商品/研究表不存在 = 数据缺口" | ⚠️ 是本地迁移未执行，不等于线上无数据 |

### 1.2 两个具体的误判证据

**（1）国债收益率：474 行 = 单页截断的特征值**

`backend/services/fetchers/valuation.py` 中 `fetch_cn_10y_bond_yield()` 的注释：

> 东财接口单页上限实测被服务端截断（**ps=5000 只回 ~473 行**），必须翻页拉全量：首页读 `result.count/pages`，之后按 `pageNo` 逐页取，去重后按日期升序返回。返回**全部历史行（按日期升序，2005 年起）**。

本地库 `cn_bond_yield` 恰好 **474 行**，覆盖 2024-10-12 ~ 2026-09-04（约 474 个交易日）。接口按日期降序返回（`sr=-1`），取第一页即得"最近 474 天"——**与"只拉了第一页"完全吻合**。

结论：本地数据是**翻页逻辑加入前**抓取的遗留，不是数据源上限。

**（2）指数股息率：源端返回的是全历史序列**

`parse_index_dividend_yield_rows()` 的输入是易方达 CDN 的 `index_dividend_ratio_{code}.json`，**返回整个历史数组**，函数还专门输出 `result["history"]`（全历史序列，供画折线图）。分位是在本地按 1Y/3Y/5Y/10Y 窗口计算的（窗口样本 < 20 则跳过）。

本地库 16 行 = 8 个指数 × 2 天，是任务只跑了 2 天的结果。

### 1.3 仍待线上确认的清单

不臆断线上，但这几项建议对照线上库核一遍，因为它们直接影响 V1/V2 的可行性：

| # | 待确认项 | 为何重要 |
| --- | --- | --- |
| 1 | `index_daily_quote` 是否覆盖 `index_eod.yaml` 配置的全部 10 个标的 | 本地只有 930955 / 399373 / 399376 / 399296 四个，**沪深300 无日线**。风格地图与回测的价格腿依赖它 |
| 2 | `cn_bond_yield` 是否仍是 474 行 | 若线上也是 474，说明翻页逻辑未生效（**可能是真 bug**），股债性价比就只有 2 年 |
| 3 | `index_dividend_yield` 的历史累积方式 | 任务是"每次全量回填"还是"每日只加最新一条"？若是后者，历史长度 = 任务运行天数 |
| 4 | `index_valuation_snapshot` 中 930955 的起点是否为 2017-05 | 若是，这是**数据源上限**（非抓取问题），直接锁死估值择时的可用区间 |
| 5 | alembic 迁移是否已在线上执行 | 本地无 `alembic_version`，`commodity_*` / `research_*` / `jisilu_*` 表均不存在。脚本齐备（0001~0004），但本地从未执行 |

### 1.4 一条不依赖本地库的统计约束（仍需确认）

若第 4 项确认为"930955 估值自 2017-05 起"，则红利估值择时的可用区间 ≈ 9.4 年（2017-05 ~ 2026-09，本地实测 2255 个交易日）：

```
24 个月持有期：N_eff ≈ (9.4 − 5年分位预热) / 2 ≈ 2.2 个
12 个月持有期：N_eff ≈ (9.4 − 5) / 1     ≈ 4.4 个
```

**N_eff 在 2~4 个量级时，任何"估值择时有效"的结论都不可靠。** 这不意味着不能做——而是第一版能交付的是框架、口径和可复现的 Run，不能据此调参或下结论。

注意这条与"本地没抓数据"无关：它取决于**指数估值数据本身的历史长度**，请对照线上确认。

**认同，无保留。** 尤其是"页面不再围绕数据源组织，而围绕决策流程组织"——当前 `AppLayout` 按"转债/市场/股票/研究/系统"分组，正是数据源视角。**【代码事实】**

### §二 新建 `/dashboard` 市场总览

**认同，且这是投入产出比最高的一步。** 顶部 8 个状态卡片的选法也对。

| 股债性价比 | E/P − 10Y 国债收益率 | 分母必须写死为 10Y；当前仅 930955 和 000300 开了 `spread_overlay` |
| 成长 − 红利 | 399376 − 930955 的 60 日收益差 | 两条日线均有 |

### §三 `/valuation` 升级为资产性价比中心（绝对 / 相对 / 趋势 / 风险）

**认同四维度框架，这是本次升级里最有价值的产品化设计。**

**一个正面发现【代码事实 + 本地数据印证】：估值数据天然无前视偏差。**

`index_valuation_snapshot` 是日频追加（唯一约束 `index_code + trade_date`，注释明确"全量保存、不覆盖历史、支持回溯任意交易日"），且**9 档分位由易方达源端在当日算好、随数据一起返回**（3M/6M/1Y/2Y/3Y/5Y/10Y/YTD/成立以来）。

这意味着历史上任何一天都能取到"当天可见"的 PE 分位，不需要自己滚窗口重算，也不会用到未来数据。做估值择时回测的底座比预想的扎实。

代价：**分位周期只能用源给的 9 档**，不能自定义（要"过去 8 年分位"就没有，只能取 5Y 或 10Y）。

**三个需要定死的口径：**
1. **相对估值的分母**：`cn_bond_yield` 有 2Y/5Y/10Y/30Y，方案写 10Y——要写死，且所有资产统一，否则跨资产不可比。
2. **回撤（DD）的基准**：从区间内高点回撤，还是滚动 1 年窗口？建议明确为"自区间内高点"，否则不同资产不可比。
3. **趋势用哪条价格序列**：需确认第 §1.3 第 1 项（10 个指数日线是否齐全）。

### §四 `/style-map` 风格地图（20/60/120/250 四周期）

**认同方向，但与现有实现有两个落差：【代码事实】**

**落差 1：现有算法是单周期的。** `style_rotation_analysis.py` 参数为 `return_window`（默认 250）+ `ma_window`（默认 20）。一次请求只算一个周期。要做四周期矩阵，需把 `spread` 从一维数组改成二维（改造量不大）。

**落差 2：分位用 `expanding` 累积，不是滚动窗口。** 现有 `p90_dynamic/p10_dynamic` 用 `expanding(min_periods=20).quantile()`，从序列起点一路累积到当前。副作用：**早期样本少时分位数不稳，且分位随时间漂移**——2012 年的分位和 2026 年的分位不是同一个分布。建议改为**滚动 N 年窗口分位**（如 rolling 750 日）。

**关于 5 个风格对的可行性**（依赖 §1.3 第 1 项确认）：

| 风格对 | 左 | 右 | 说明 |
| --- | --- | --- | --- |
| 成长 − 红利 | 399376（2012-） | 930955（2005-） | 两端日线本地均有，可做 |
| 小盘 − 大盘 | 399376 | 399373 | 均自 2012，可做 |
| 价值 − 红利 | 931052 / 980081 | 930955 | 价值指数日线需确认 |
| 转债 − 红利 | `cb_index_daily` | 930955 | 等权指数起点需确认 |
| 纳指 − 红利 | — | 930955 | **纳指不在任何配置里**，需新增标的 |

建议：**先上标的确定的 2 对**，其余等确认后再加。**不要用代理资产凑数**——方案自己在前一版文档里强调过"中国海油 ≠ 原油"的代理风险，这里同样适用。

### §五 `asset_master` 统一资产主表

**强烈认同这是关键一步，但要修正前提：不需要新建，`index_universe` 已完成 80%。【代码事实】**

`backend/services/index_universe.py` 已实现：

- **单一事实源**：合并 `config/valuation.yaml` + `config/index_eod.yaml` + 腾讯常量
- **dataset 绑定**：每个资产按 `quote` / `valuation` 分别绑定数据源（efunds / tencent）
- **`symbol` 与 `storage_code` 解耦**：抓取用真实指数代码（931052），历史存储用旧配置代码（512040），保证既有数据不重写、新抓取不查错表——这正是统一资产主表最难的部分
- **运行时落点**：`data/index_universe.json`（不进 git，原子写）
- **任务路由**：`datasets_for_job(job_id)`
- **开关**：资产级 + dataset 级 `enabled`

**缺的正是方案列的字段**：`asset_class`、`style`、`region`、`currency`、`benchmark_type`、`proxy_for`、`is_benchmark`、`is_tradeable`。补上即可。

**一个需要拍板的架构选择**：`index_universe` 现在是 **JSON 文件**而非 DB 表。JSON 简单、可手工编辑；但无法 JOIN、无法被外键引用，组合/回测表要关联资产时只能冗余存 code。

我的倾向：**JSON 作配置源（"声明"）+ `asset_master` DB 表作运行时索引（"注册"）**，启动时同步进表。这样组合/回测可外键引用，又不牺牲可编辑性。

### §六 `/portfolio-lab` 组合实验室（第一版只做固定权重 + 回测）

**认同"先证明多资产组合本身有没有改善回撤，不要一上来做风险平价"。**

**但 §零 第 3 条的 Benchmark 口径问题必须先解决。** 补充验证方法与备选方案：

1. **验证**：取 930955 某次除息日的点位序列，与中证官方全收益指数对比，看除息日是否出现向下跳空（价格指数会因除息自然回落，全收益不会）。
2. **若为价格指数**，二选一：(a) 引入全收益指数数据源；(b) 用股息率手工加回——股息率有全历史序列（§1.2），(b) 技术上可行。
3. **在口径确定前**，所有回测结果必须带标注："基准为价格指数，未计股息"。

**另外三个方案未定义、但回测必须定的参数：**
- **调仓执行价**：收盘价成交还是次日开盘？指数只有 close，实际只能按收盘——要在文档里写明这个妥协。
- **交易成本**：费率、印花税、冲击成本的默认值。
- **多资产日历对齐**：A 股 / 港股 / 海外日历不同，`inner join` 会剔除缺失日；各腿起点差异巨大，多资产回测的公共区间被最短的那条锁死。这个要在回测结果里显式报出"实际有效区间"。

### §七 策略组合（统一 `target_weights` 接口）

**完全认同，这是防止"每研究一个想法就写一份独立脚本"的唯一办法。**

补充：**这套抽象 `/research` 已经跑通了一个更严格的版本【代码事实】**。`research_plan.py` 的 `generate_plan()` 是纯函数、零 DB 依赖、带 `ALGORITHM_VERSION` 常量，注释明确："线上与历史回放共用本模块的一份计算逻辑；指标初始化/公式任何变更必须升 ALGORITHM_VERSION"。

这个"线上线下共用一份计算逻辑 + 算法版本号"的约定应直接搬到组合策略接口上。否则回测用 A 逻辑、线上跑 B 逻辑，是最难查的一类 bug。

### §八 `/backtest` 回测中心

**认同，且"防止自我欺骗工具"这个定位说得很准。**

**但要修正前提：实验保存范式不需要从零设计，`/research` 已有一套成熟的，抽象复用即可。【代码事实】**

`research_replay_run` 表字段：

```
symbol, param_lambda, quantile_window, algorithm_version,
start_date, end_date, train_end_date, train_days, validation_days,
raw_snapshot_id, hfq_snapshot_id, input_hash, status, error, created_at
唯一约束: (symbol, param_lambda, quantile_window, algorithm_version, start_date, end_date)
```

关键点：
- **参数即身份**：参数组合构成唯一键 → 同参重跑不产生新 Run，改任一参数即新 Run。这正是 §九 要的"参数改一次就是新实验，不覆盖旧结果"。
- **`input_hash`**：记录输入数据哈希，数据变了可追溯。
- **内置样本内外切分**：`train_end_date` / `train_days` / `validation_days`。
- **已有对比接口**：`GET /api/research/replay-comparison`。

**建议**：把 `research_replay_run` 抽象成通用 `backtest_run` 范式（策略标识 + 参数 JSON + 资产池哈希 + 数据截止日 + 算法版本 + 输入哈希 + 区间），两边共用同一套实验管理与对比 UI。

### §九 实验强制保存版本

**认同，见 §八——机制已存在，推广即可。** 需补充方案提到的"因子版本"和"数据截止日期"两个显式字段（`input_hash` 与 `train_end_date` 语义接近但不够显式）。

### §十 `/research-hypotheses` 研究假设页面

**认同，它补上了当前系统最大的空白：记录"最开始为什么研究这个东西"。**

**方案说"若 `/research` 已有类似能力，就基于它扩展"——答案是：有，但它是回放引擎而非假设管理。【代码事实】**

现有 `/research` 的能力（源码层）：

- **结构性防前视**：`generate_plan()` 第一行过滤 `date <= T`，T+1 数据在结构上进不来
- **数据完整性**：raw/hfq 配对抓取快照，两侧不完整则整批 REJECTED；`content_hash` + `research_data_revision` 保留供应商修订的完整旧载荷
- **权益事件处理**：事件日历为主检测 + `r_t` 相对阶跃兜底（腾讯源非事件日有 0.1%~0.4% 抖动，故容差放宽到 5%）
- **指标**：EMA20（种子=前 20 根均值）、Wilder ATR14、ATR 归一化的上下行偏移样本、线性插值经验分位
- **六档价位**：`buy/sell_levels_raw`，**未取整的"模型价"，明确不得显示为可下单报价**
- **逐日明细**：z 值、ATR、EMA、scale、六档价、次日 OHLC、逐档命中布尔、开盘失效标记
- **九类日分类**：`BUY_ONLY` / `SELL_ONLY` / `BOTH_HIT` / `NO_HIT` / `DISABLED` / `EXCLUDED_DATA` / `EXCLUDED_CORP_ACTION` / `EXCLUDED_OPEN_INVALIDATION` / `CALENDAR_UNVERIFIED`
- **口径谨慎**：注释明确"开盘失效的一侧不进入该侧档位命中率分母"

**所以 §十 的假设页面应是"元层"**：一条假设（如 H001：EP−10Y 越高，红利未来 12M 收益越高）关联 N 个验证实验，每个实验就是一次 Run。假设管理是新的，实验执行复用现有范式。

### §十一 `/execution` 执行研究（含做 T）

### §十三 接口从"全量返回"改为分页

**认同，已核实确认【代码事实】：** 57 个端点中只有 `GET /api/data-management/runs` 有 `limit`（1~200），其余全部全量返回。新增 `/api/backtest/*` 一开始就分页——同意。

补充两点：
- **NAV 序列不适合 JSON 全量返回**（数千交易日 × 多组合），除分页外还应支持**降采样**（画图只需每周一个点）。
- **回测计算应异步化**：见 §十四 的 SQLite 并发约束。

### §十四 数据库从"页面模型"转向"研究模型"

**认同建领域表，但有三个工程约束方案没考虑：**

**约束 1：SQLite（WAL，本地库 24MB）。【代码事实】**
`backtest_nav`（每日 × 每个 Run）会迅速膨胀：100 个 Run × 2500 天即 25 万行/资产，很快到百万级。
建议：**NAV 序列存文件（Parquet/CSV），DB 只存 Run 元数据 + 指标摘要**。"对比两个实验"变成读两个文件，比查表快得多。

**约束 2：SQLite 并发写与回测 CPU 密集冲突。【代码事实】**
`database.py` 已配 WAL + `busy_timeout=5000`，因 APScheduler 多任务与 FastAPI 并发写同一库会锁。回测若跑在请求线程内，会长时间持锁并拖垮定时任务。
建议：**回测走独立异步任务 + 独立 session，结果写文件，只在开始/结束时写 DB 状态**。

**约束 3：本地迁移从未执行**，新增表前需先确认线上状态（§1.3 第 5 项）。

另外，方案列的 `factor_definition` / `factor_value` 两张表我建议**第一版不建**。现有因子要么由数据源直接给出（估值分位），要么可即时计算（风格差、HV）。落因子宽表会带来大量写入与版本管理成本，收益要等因子数超过 10 个才体现。

### §十五 每个页面必须回答一个问题

补一条判据：**若页面上某个数字无法追溯到 Run ID 或数据快照日期，它就不算合格。** 这能防止页面悄悄变成"只有结果没有出处"的装饰。

## 三、被低估的三件事

1. **`/research` 的工程价值【代码事实】**。它不是"做 T 的一个页面"，而是一套已跑通的**实验管理范式**（参数即身份、输入哈希、算法版本、样本内外切分、对比接口、结构性防前视）。推广到组合回测可省掉大量设计工作。
2. **`index_universe` 的完成度【代码事实】**。方案想要的 `asset_master` 八成已存在，且已解决最难的部分（同一资产在不同数据源下代码不同 → `symbol` / `storage_code` 解耦）。
3. **估值数据的质量【代码事实 + 本地印证】**。日频追加 + 源端分位 = 天然无前视、历史长（本地实测 000300 自 2005 年、26,052 行）。这是系统里最扎实的一块，方案只提到"PE/PB/多周期分位"，低估了它。

## 四、需要拍板的问题

1. **Benchmark 口径**：确认现有指数日线是价格指数还是全收益？若是价格指数，引入全收益数据源，还是用股息率手工加回，还是统一标注"未计股息"？（**V2 之前的头号问题**）
2. **§1.3 的 5 项线上确认**：能否提供线上库各表的 `COUNT(*)` 与 `MIN/MAX(trade_date)`？特别是国债收益率是否仍为 474 行（若是，翻页逻辑可能是 bug）。
3. **`asset_master` 落 DB 表还是继续用 JSON**：我倾向 JSON 作配置源 + DB 表作运行时索引。
4. **"我的组合"做真实持仓还是目标权重**：我建议第一版只做目标权重。
5. **风格地图先上几对**：建议先上标的确定的 2 对，不用代理资产凑数。
6. **`factor_definition` / `factor_value` 是否第一版就建**：建议暂缓，因子数 >10 再建。

con = sqlite3.connect('<线上库路径>')
cur = con.cursor()
cur.execute(\"SELECT name FROM sqlite_master WHERE type='table' ORDER BY name\")
print('TABLES:', [r[0] for r in cur.fetchall()])
print()
for t in ['index_valuation_snapshot','index_daily_quote','index_dividend_yield','cn_bond_yield','cb_index_daily','cb_daily_snapshot']:
    try:
        cols=[c[1] for c in cur.execute(f'PRAGMA table_info(\"{t}\")').fetchall()]
        key='index_code' if 'index_code' in cols else None
        if key:
            cur.execute(f'SELECT {key}, COUNT(*), MIN(trade_date), MAX(trade_date) FROM {t} GROUP BY {key}')
        else:
            cur.execute(f'SELECT COUNT(*), MIN(trade_date), MAX(trade_date) FROM {t}')
        print('==', t)
        for r in cur.fetchall(): print('  ', r)
    except Exception as e:
        print('==', t, 'ERR', e)
"

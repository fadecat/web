> 目标：为组合回测实验室建立**稳定数据底座**。
> 标注约定：**【实测】** = 本次在本机（经代理出口）真实调用获得；**【代码事实】** = 本仓库源码/文档已核实；**【待验证】** = 必须在 ECS 上实测，本机结果不能作为证据。

## 结论先行

1. **股票日 K 与 ETF：数据源已经解决，不需要找新源。** 腾讯 `fqkline` 已于 2026-09-18 在 ECS 按 PoC 级验收，支持 raw/hfq 后复权，**股票与 ETF 统一**（成交量单位均为"手"，权益事件日历同源）。当前短板只是**标的数量**（`config/research.yaml` 里 5 个），加一行配置即可扩容。
2. **场外基金：改用蛋卷基金（danjuanfunds.com），天天基金降级为备选。**【ECS 实测】蛋卷 `/djapi/fund/nav/history/{code}?page=&size=` 的 `size` 可达 **6000**，一只 2003 年成立的老基金 **1 个请求即拉完全部 5545 行**（区间 2003-12-02 起 = 成立以来全历史）；无 Referer 依赖、无需登录。**选它的核心依据是请求数最少**：

   | 源 | 单页上限 | 一只 20 年基金全历史的请求数 |
   |---|---|---|
   | **蛋卷 `djapi`** | **6000** | **1** |
   | 天天基金移动端 | 1000 | 7 |
   | 天天基金 Web | 20 | **301** |

   请求数少 1~2 个数量级，本身就是**对数据源的克制**，也顺带把触发风控的概率降到最低。天天基金在 ECS 上触发限流后 **≥30 分钟不可用**（15 轮 × 2 分钟观测，成功 0/15），故降为兜底与交叉校验源。
3. **ECS 可达性已实测完成**（详见 `docs/data-source-ecs-probe-report.md`）。腾讯 fqkline **OK**；蛋卷 **OK**；天天基金 **可用但限流窗口 ≥30 分钟**；东财 `push2his` **BLOCKED**（封禁仍在）。
4. **使用纪律**：本项目对第三方数据源保持克制使用（参照集思录的既有做法）。探针脚本只做接口结构验证、请求数控制在个位数；**禁止连发探测、批量拉取、压测**。评估数据源看"完成一次任务需要多少请求"，不看"能承受多大并发"。

## 一、股票 / ETF：现状即答案，不用另找

【代码事实】`docs/superpowers/specs/2026-09-18-next-day-t-research-replay-design.md` §9 数据源决策记录：

| 项 | 结论 |
|---|---|
| 接口 | `web.ifzq.gtimg.cn/appstock/app/fqkline/get`，`fq=''`(raw) / `'hfq'` |
| 复权 | raw + hfq 双模式，hfq 为后复权连续序列 |
| ETF 支持 | **已实测通过**（510300、511010 正在跑）；股票与 ETF 成交量单位均为「手」，统一 ×100 → 股/份 |
| 权益事件 | 新浪 `hfq.js`，股票与 ETF 统一口径 |
| 分页 | 单次上限 640 条，按「窗口内最新 count 条」向后游标分页 |
| 限流 | 12 连发（0.3s 间隔）通过；标的×模式之间礼貌间隔 2s |
| 交易日历 | 新浪 `tool_trade_date_hist_sina`，已落 `research_trade_calendar` |

**已知的两个坑（已在处理，扩容时会再遇到）：**

- **ETF hfq 发布滞后**：腾讯 ETF 的 hfq 当日 bar 晚于 raw 发布，曾导致整标的 REJECTED。任务层已加"尾部发布滞后截齐"（仅当长侧多出的 bar 全部晚于短侧末日且 ≤5 根时截齐）。
- **hfq 比值抖动**：`r_t = raw_close/hfq_close` 在非事件日有 0.1%~0.4% 抖动（601288 最大 6.8%），与真实分红事件量级重叠 → r_t 阶跃启发式不可用，权益事件改以新浪事件日历为主检测。

**扩标的成本**：`config/research.yaml` 加一行 → 跑 `research_daily_sync`。无新数据源、无新代码。

请求   GET /djapi/fund/nav/history/100018?page=1&size=6000
结果   5545 行 / total=5545 / 1 页 / 411,961B / 0.6s

```

> **使用纪律**：调研期间曾为摸清边界做过连发与批量实验（连发 10 次、批量 5 只），**这类做法不应重复**——本项目对第三方数据源保持克制使用（参照集思录：日登录次数受限、落盘 cookie 复用会话、定时任务只在收盘后与深夜各跑一次）。探针只做接口结构验证、请求数控制在个位数。**一只基金 1 个请求这件事本身，比"能连发多少次"更值得作为选型依据。**
```

**两个必须注意的点：**

1. **`value` 字段恒等于 `nav`，不是累计净值。** 实测 000001 全部 6000 行 `nav == value`。蛋卷没有直接给累计净值——但不影响，因为 `percentage` 已经是分红再投口径，可直接链式复利构造复权净值（见第三节）。
2. **申赎费率在另一个接口**：`/djapi/fund/{code}` 的 `fund_rates`（实测 `{"subscribe_rate":"1.0","declare_rate":"1.2","discount":"0.1","subscribe_discount":"1","declare_discount":"0.1"}`，单位百分数）+ `declare_status` / `withdraw_status` 申赎状态。**这正好补上天天基金移动端缺失的字段**，且蛋卷无需登录。

> 注：探针为 `scripts/probe_danjuan.py`（**克制版**：只做接口结构验证，默认 1~3 个请求，标的数 >5 直接拒绝执行）。我们的场景是组合回测，一个组合通常只有几只标的——**请求数控制在个位数即可，不做压测**。

**推荐方案**：蛋卷做净值全历史回填（1~2 页/基金）+ 蛋卷 `/djapi/fund/{code}` 补申赎费率与状态；天天基金保留为同源交叉校验的备选。

## 三、口径陷阱：这三条决定收益算得对不对

### 1. 单位净值 ≠ 累计净值 ≠ 复权净值（最容易错的一步）

| 字段 | 含义 | 能否直接算收益 |
|---|---|---|
| `DWJZ` 单位净值 | 分红日**除权跳空** | ❌ 系统性低估 |
| `LJJZ` 累计净值 | = 单位净值 + 累计每份分红，等价于"分红以现金持有、不再投入" | ❌ 仍低估（分红部分不计息增长） |
| `JZZZL` 日增长率 | 基金业按**分红再投资**口径披露 | ✅ |

| 蛋卷 `percentage` 日增长率 | 同 `JZZZL`，**已实测确认是分红再投口径**（见下） | ✅ |

**正确口径**：用日增长率链式复利构造复权净值序列——

```
NAV_adj,t = NAV_0 × Π(1 + JZZZL_i / 100)      # 天天基金
NAV_adj,t = NAV_0 × Π(1 + percentage_i / 100) # 蛋卷
```

**蛋卷 `percentage` 的实证**（000001，2006-03-22 ~ 2026-09-18，4999 个交易日）【实测】：

- 4978 天满足 `percentage ≈ nav_t/nav_{t-1} - 1`（容差 0.03%）；
- **21 天不满足，且全部是"nav 大跌、percentage 仅小跌"** —— 即分红除权日。例：
  - 2017-12-07：nav 由 1.1920 → 1.1000（**−7.72%**），`percentage = −1.01%` → 差额 6.7% 是分红
  - 2015-11-20：nav −5.23%，`percentage = +1.56%`
- **累计对比**：直接用 `nav` 首尾相比 = **1.2446x**；`percentage` 链式复利 = **7.2337x**。差异 **+481%**。

> 这个数字就是最直观的警告：若图省事直接拿单位净值算收益，20 年下来会低估到 1/5.8。而误差方向恰好会让"多资产组合跑不赢红利"的结论显得更糟。**必须写进适配器，不能靠下游注意。**

### 2. 净值公布时点 → 两个后果

- T 日净值在 **T 日晚间（常见 20:00~23:00）**才公布；QDII 基金（如场外纳指基金）为 **T+1/T+2**。
- 后果一：定时抓取必须晚于公布，且要处理"当日可能尚未公布"的空窗（幂等重试，不能把缺失日写死）。
- 后果二：回测中"T 日按 T 日净值成交"是**前视**。这印证了前一轮的建议——场外基金默认 **T+1 成交**（T 日信号 → T+1 净值成交）。

### 3. 申赎状态与跨资产口径不等价

- `SGZT`/`SHZT` 会给出"限购 / 暂停申购 / 封闭期"。回测时若当日不可申购，就不能建仓——移动端接口**没有这两个字段**，需用 Web 接口补齐或单独维护。
- **ETF 的后复权（税前分红再投）与场外基金的累计收益率（税后、按当日净值再投）口径并不等价**。同一组合里混放两类资产时，引擎必须显式记录 `price_type`，否则跨资产比较带无声偏差。

## 五、三源打通的最小路径

用户明确：**组合回测一个组合只有几只标的，够用即可，不要为百只级批量做过度设计。** 据此收敛为三条腿：

| 资产 | 数据源 | 状态 | 打通动作 |
|---|---|---|---|
| A股个股 / ETF | 腾讯 `fqkline` | 已验收 | 扩 `config/research.yaml` 标的即可，零新代码 |
| 场外基金 | 蛋卷 `/djapi/fund/nav/history/{code}` | ECS 实测 OK | 建表 → 迁移 → fetcher → 任务 → 接入 `get_series` |
| 指数基准 | 易方达 `index_eod_price`（线上 12 个指数 / 2002 起） | 已就绪 | 待定口径（见第六节） |

**场外基金链路的极简设计**（只服务"几只标的"）：

1. 单表 `fund_nav_daily`：`code`, `trade_date`, `unit_nav`, `daily_return_pct`, `adj_nav`（由 `daily_return_pct` 链式复利在本地算好并落库）。
2. fetcher：`size=6000` 单页拉全历史 + 按 `total_pages` 兜底第二页；日频增量只拉 `page=1&size=5`。
3. 无需并发、无需限速器——**因为一只基金全历史只需 1~2 个请求**，串行 + 标的间 3s 礼貌间隔即可（把请求数压到最低本身就是最好的限速）。
4. 申赎费率/状态：`/djapi/fund/{code}` 按需单次拉取，不入时序表。

**不再做的事**：对第三方数据源的任何压测/连发探测/批量回填实验（**用户明确要求：对对方服务器保持克制**）、多源并发架构、分布式限速器。

## 附：一个顺带发现（不在本次范围，但影响基准）

组合回测需要指数基准，而现有指数日线（易方达 `index_eod_price`）**只有 close**，疑为价格指数、不含股息再投入——这是"相对红利超额"这条指标的生死线。腾讯 `fqkline` 理论上可取指数序列，但当前 `_assert_symbol_type` 只认 `STOCK`/`ETF`，需扩展 `INDEX` 类型。这个可以放到基准口径拍板之后一起做。

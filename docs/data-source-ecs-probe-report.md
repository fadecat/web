## 二、数据源可达性实测（ECS 出口 IP）

| 源 | 判定 | 实测细节 |
| --- | --- | --- |
| 腾讯 `fqkline` 日线 | **OK** | HTTP 200 / 2271B，股票与 ETF 统一口径 |
| 天天基金 Web `api.fund.eastmoney.com/f10/lsjz` | **OK** | `rows=5`，含 `SGZT`/`SHZT`/`FHFCZ` 完整字段 |
| 天天基金移动端 `fundmobapi.../FundMNHisNetList` | **可用但限流** | 单发成功时返回 **117,669 B / 1000 行**；连续请求触发 `ErrCode=61136403` |
| 东财 `push2his` 行情 | **BLOCKED** | `RemoteProtocolError: Server disconnected without sending a response`（连接被重置） |

### 限流的具体表现

东财系被限流时**仍返回 HTTP 200**，响应体为：

```json
{"Datas":null,"ErrCode":61136403,"Success":false,"ErrMsg":"网络繁忙，请稍后重试！","TotalCount":0}
```

**这是本次实测最重要的工程细节**：绝不能用"响应体里有没有 `Datas` 这个子串"来判断成功——错误响应里也有 `"Datas": null`。我把探针的判定逻辑从子串匹配改成了 **payload 非空校验**，并新增 `RATE_LIMITED` 状态与 `ErrCode` 识别。

### 受控实验（区分限流因子）—— 仅作记录，不应重复

> ⚠ **这类实验（19 次请求探测限流因子）本身就是对数据源的不当使用，仅为摸清边界而做，不应重复。** 正确做法是直接按"窗口性限流、≥30 分钟不可用"的保守口径设计抓取器，不需要去测出准确阈值。详见第五节的使用纪律。

在 ECS 上跑了 4 组共 19 次请求，结果**全部限流**：

| 组 | 变量 | 结果 |
| --- | --- | --- |
| A | 新建连接，间隔 3s ×5 | 0/5 |
| B | 复用连接，间隔 3s ×5 | 0/5 |
| C | 新建连接，间隔 8s ×4 | 0/4 |
| D | 新建连接，间隔 3s + Referer ×5 | 0/5 |

结论：**不是连接复用问题，也不是 Referer 缺失，也不是 3s 太短**——当时整体处于封禁窗口内。

而在此前与此后，同样的接口都有单次成功记录（117KB / 1000 行、以及间隔 3s 的 Web+移动端双双成功）。因此判定为：

> **IP 级窗口性限流，非永久封禁；但冷却窗口 ≥30 分钟、期间零恢复（见下）。**

### ⚠ 冷却时长：实测 ≥30 分钟且期间零恢复（结论已收敛）

触发限流后启动的低频观测（每 120s 单发 1 次，共 15 轮 / 30 分钟），**完整结果**：

```
[01:34:58] start rounds=15 cooldown=120.0s
[01:34:58] round  1: 首发 LIMIT (ErrCode=61136403)
[01:36:59] round  2: 首发 LIMIT (ErrCode=61136403)
   ...（中间 3~14 轮全部 LIMIT，间隔严格 120s）...
[02:01:00] round 14: 首发 LIMIT (ErrCode=61136403)
[02:03:00] round 15: 首发 LIMIT (ErrCode=61136403)
[02:03:00] done
```

**15 轮、跨度 30 分钟、成功率 0/15。** 每 2 分钟才 1 次请求仍然全被拒，说明这不是"降频即可规避"的速率限制，而是触发后的**冷却窗口**，与项目历史上记录的 push2 族"封禁 30 分钟+"属同一类机制。

修正此前的一处乐观表述：原判断写的是"冷却后自动恢复"，但本次观测在 30 分钟窗口内**没有观测到任何一次恢复**。因此工程上应按"触发后至少 30 分钟不可用"来设计，不能假设数分钟内可重试成功。

**对方案的影响（必须正视）**：

| 场景 | 可行性 |
| --- | --- |
| 单只基金全历史回填（7 页） | **不稳定**。窗口外可行，但一旦触发需等待 ≥30 分钟；无法作为可预期的批量流程 |
| 日频增量（每日只拉最新几行） | 可行，请求量极小（1~2 次/只/日），可加退避重试兜底 |
| **批量回填数百只基金** | **不可行**。按 ≥30 分钟窗口估算，回本时间不可接受 |

这条结论的直接推论：**场外基金不适合作为组合回测的主力资产面**（见第六节的替代路线）。

## 三、对抓取器实现的硬约束

1. **单基金串行拉取**，不做并发——并发会迅速触发风控。
2. **页间隔**，且失败后**指数退避**（`gap × 2^attempt`），重试上限 3~4 次。
3. **按基金维度断点续传**：记录已完成的 `pageIndex`，下次从断点继续，避免失败后整只基金重来。
4. **日频增量只拉最近**，全历史回填仅首次执行。
5. **移动端为主、Web 为辅**：移动端 pageSize=1000 做全历史（7 页）；Web 接口 pageS上限 20，仅在需要 `SGZT`/`SHZT`/`FHFCZ` 分红与申赎状态字段时补近端。
6. **口径**：用 `JZZZL`（日增长率，分红再投资口径）链式复利构造复权净值，不能用 `DWJZ`（除权跳空）或 `LJJZ`（累计净值，等价于现金分红不再投）。

## 五、限流窗口观测结果（已结束）

为给出窗口量级，曾在 ECS 上跑了 15 轮 × 2 分钟、跨度 30 分钟的低频观测（每轮单发 1 次，成功则再连发 2 次）。

**结果：15 轮成功 0 次，全程零恢复。**

因此本报告按**"触发后 ≥30 分钟不可用"**这一保守口径使用，不再假设"冷却后自动恢复"。

### 使用纪律（重要，勿破例）

本项目的既有做法是**对第三方数据源保持克制使用**——集思录即为例证（日登录次数受限、落盘 cookie 复用会话、定时任务只在收盘后与深夜各跑一次）。本次调研期间为探测边界做过若干连发实验，**这类做法不应成为常规**：

- 探针脚本只用于**接口结构验证**，默认 1~3 个请求；禁止用于压测、连发探测、批量拉取。
- 批量抓取一律走正式 fetcher：**单标的串行 + 页间隔 + 指数退避 + 断点续传 + 日频增量只拉最近**。
- 选型时优先看**完成一次任务所需的请求数**（越少越克制），而不是"能承受多大并发"。

这条纪律也直接改变了场外基金的选型结论（见第五之二）。

## 五之二、场外基金：蛋卷基金（danjuanfunds.com）—— 当前最优解

在东财系（天天基金）存在窗口性限流的前提下，验证了**蛋卷基金**（雪球旗下，域名与东财不共享风控）作为替代源。

### 接口

| 用途 | 端点 |
| --- | --- |
| 历史净值 | `GET /djapi/fund/nav/history/{code}?page=&size=` |
| 基础信息 | `GET /djapi/fund/{code}` |

两者**均无需 cookie、无 Referer 依赖**，直接可用。

### 关键优势：请求数最少（这才是"克制"的正确度量）

历史净值响应自带 `total_items` / `total_pages`，且 **`size` 支持到 6000**。实测一只 2003 年成立的老基金：

```
100018 富国天利增长债券:  5545 行 / total=5545 / 1 页 / 411,961B / 0.6s
                        区间 2003-12-02 ~ 2026-09-18   ← 成立以来全历史
```

**一只基金的全历史只要 1 个请求。** 三个源对比：

| 数据源 | 每页条数上限 | 一只 20 年基金的请求数 |
| --- | --- | --- |
| **蛋卷 `djapi`** | **6000** | **1** |
| 天天基金移动端 | 1000 | 7 |
| 天天基金 Web | **20** | **301** |

> 这个维度比"是否限流"更值得作为选型依据：请求数少 1~2 个数量级，既是**对数据源的克制**，也把触发风控的概率降到最低。

### 字段口径（已验证，含一个坑）

```json
{"date": "2026-09-18", "nav": "1.3684", "percentage": "0.04", "value": "1.3684"}
```

- **`percentage` = 分红再投口径的日增长率（%）** ✅ 可直接用于构造复权净值。
  验证方法：找"单位净值跳空但 `percentage` 平滑"的日子。100018 全历史有 **52 处**此类背离，例如 `2026-03-17`：单位净值口径 **−2.08%**，而 `percentage` 为 **−0.04%**——差额即当日分红。
  累计效果（000001 华夏成长，2006-03-22 ~ 2026-09-18）：单位净值口径 **1.24x**，链式 `percentage` 口径 **7.23x**，**差 4.8 倍**。若误用单位净值当收益序列，整条腿会严重低估。
- **⚠ 坑：`value` 字段恒等于 `nav`，并非"累计净值"**。不要把它当作复权序列，必须自己从 `percentage` 链式累乘：

  ```
  NAV_adj,t = NAV_0 × Π(1 + percentage_t / 100)
  ```

- 精度：`percentage` 为 2 位小数（天天基金 `JZZZL` 精度更高）。日频舍入误差近似随机，20 年累积影响在 1% 量级——对组合层面的结论不构成实质影响，但**单日收益的精确复现应以单位净值为准交叉校验**。

### 基础信息接口的额外价值

`/djapi/fund/{code}` 返回的字段**正好补齐了天天基金移动端缺失的部分**：

```json
"found_date": "2003-12-02",
"declare_status": "1",  "withdraw_status": "1",     ← 申赎状态
"risk_level": "2",      "manager_name": "黄纪亮",   ← 风险等级/基金经理
"keeper_name": "富国基金管理有限公司",  ← 基金公司
"fund_rates": {"subscribe_rate": "1.0", "declare_rate": "1.2",
               "subscribe_discount": "1", "declare_discount": "0.1"}   ← 申赎费率
```

申赎费率可直接支撑组合回测的交易成本分档（此前列入待办）。

### 结论

**蛋卷基金取代天天基金，作为场外基金的主数据源。** 理由不是"能扛并发"，而是：请求数少一个数量级（1 vs 7 vs 301）、字段口径明确且可验证、无需 cookie、补齐了申赎费率与状态字段。

保留天天基金为**兜底源**：两者字段可互相交叉校验（`percentage` vs `JZZZL`），且东财 Web 端字段最全。

探针脚本：`scripts/probe_danjuan.py`（**仅作接口结构验证，默认 1~3 个请求**）。

| 估值指标（日频） | 仅沪深 A 股 | — | **指数不提供估值**，无法替代现有估值链路 |
| 财务/宏观 | 季频财务、存款/贷款利率、货币供应量等 | 2007 / 1990 起 | 当前非需求 |

其他特性：`pip install baostock`、**无需注册**、每日 17:30 完成日K入库、18:00 完成复权因子入库。

**评估结论：Baostock 不解锁任何新能力，不应进入关键路径。**

1. **ETF 腿（组合回测的主力资产面）**：Baostock 的 ETF 数据只到 2026-01-05，而我们需要的是 10 年以上的多资产序列。**腾讯 `fqkline` 无可替代。**
2. **Benchmark 口径问题**：Baostock 的指数同样是价格指数，且明确"指数未提供估值数据"。我们线上已有 12 个指数、2002 年起（易方达源），覆盖比 Baostock 更长。**引入它解决不了那个硬阻塞。**
3. **唯一边际价值**：个股 1990 年起的历史 + 独立复权因子，可用于**交叉校验腾讯 hfq 的复权口径**——这正是那份指南 5.1 节强调的"不同平台复权计算方式不同，建议交叉验证"，也呼应我们已知的"腾讯 hfq 比值在非事件日有 0.1%~0.4% 抖动"。

> 该指南同时指出 efinance 稳定性"低（东财 IP 限制）"、yfinance 国内不可访问、Tushare 需积分制——与本项目已有的实测结论一致，无需再评估。
